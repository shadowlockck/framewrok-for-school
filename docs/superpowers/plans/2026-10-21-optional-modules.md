# Коректне підключення необов'язкових модулів

Статус: реалізовано 2026-10-21. Результати перевірок наведено наприкінці.

## Мета

Новий або наявний сайт запускається з обраним набором модулів. API, маніфест,
меню, головна сторінка, адмінка та демодані узгоджені з `INSTALLED_APPS`.

## Виявлені місця ризику

- `backend/config/urls.py` та шаблон URL-конфігурації в `backend/apps/core/cli.py`
  безумовно підключають усі шкільні застосунки.
- `backend/apps/core/views.py` уже визначає модулі через `apps.is_installed`,
  але перелік маршрутів і перелік пунктів меню підтримуються окремо.
- `backend/apps/core/frontend_site.py` завантажує всі колекції паралельно з
  маніфестом; тип маніфесту не містить `modules`.
- `frontend/src/context/SchoolContext.tsx` має резервний маніфест з усіма
  увімкненими модулями навіть за відсутності відповіді сервера.
- `backend/apps/core/management/commands/seed_school_data.py` імпортує моделі
  всіх модулів на рівні файлу.
- `schedule.LessonSchedule.grade` посилається на `admissions.ClassCapacity`;
  початкова міграція розкладу також залежить від міграції вступу.
- Наявний smoke-тест wheel перевіряє лише повну конфігурацію.

## Контракт конфігурації

1. `apps.core` і необхідні системні/сторонні Django-застосунки обов'язкові.
2. Необов'язкові модулі: `legal`, `admissions`, `nutrition`, `safety`, `news`,
   `schedule`, `gallery`. Єдине джерело активності — реєстр Django, сформований
   з `INSTALLED_APPS`; підтримуються як шляхи застосунків, так і їх AppConfig.
3. `schedule` потребує `admissions`. При відсутній залежності `manage.py check`
   має пояснювати, який модуль додати або прибрати. Залежності не додаються мовчки.
   Винесення класів в окремий модуль — інша задача зі зміною моделей і міграцій.
4. Вимкнений модуль має `false` у маніфесті, не має пунктів меню, API-маршрутів,
   записів у OpenAPI та реєстрацій моделей в адмінці. Його API повертає 404.
5. Вимкнення означає зміну конфігурації та перезапуск, а не перемикач в адмінці.
   Дані й таблиці не видаляються. Повторне ввімкнення повертає доступ до даних.
6. За замовчуванням нові сайти отримують усі модулі. Існуючі URL, назви маршрутів,
   порядок меню і структура маніфесту зберігаються; `finance` належить `legal`.

## Послідовність реалізації

### 1. Відтворити помилки та закріпити контракт

- Створювати тимчасові проєкти й окремі бази для кожної конфігурації.
- Відтворити відключення `gallery`, запуск лише з `core` та некоректну комбінацію
  `schedule` без `admissions`.
- Додати регресійні перевірки реального запуску в окремих Python-процесах:
  зміна реєстру застосунків у вже запущеному Django може приховати імпортні помилки.

### 2. Узгодити маршрути, маніфест і залежності

- Додати в `apps.core` невеликий спільний опис вбудованих модулів: ідентифікатор,
  шлях застосунку, URL-префікс, URLconf, пункти меню та залежності.
- На його основі формувати список активних маршрутів і дані маніфесту.
  URLconf вимкнених модулів не імпортувати.
- Використати спільний помічник у демонстраційному проєкті та генераторі CLI.
- Замінити прямий імпорт `ClassCapacity` у моделі розкладу на рядкове посилання
  на модель, додати зрозумілу Django system check для залежності модулів.
  Перевірити, що валідна конфігурація не потребує нових міграцій.

### 3. Прибрати приховані залежності ядра

- Розділити наповнення демоданими на частини за активними модулями; завантажувати
  їхні моделі тільки після перевірки активності. Зберегти чинні демодані повного сайту.
- Перевірити шаблони головної сторінки, адміністративну панель, template tags,
  аудит наповнення та CLI-команди на імпорти й посилання на вимкнені модулі.
- Аудит має працювати без їхніх таблиць і не пропонувати недоступні admin URL.
  Оцінка перевірених розділів не повинна подаватися як доказ повної відповідності
  сайту лише тому, що частину розділів вимкнули. Загальний юридичний аудит поза цією задачею.

### 4. Підпорядкувати фронтенд маніфесту

- У спільному генераторі `frontend_site.py` спочатку завантажувати маніфест,
  потім запитувати колекції лише активних модулів.
- Встановити відповідність колекцій і сторінок модулям, включно з `finance → legal`.
- Узгодити меню, картки, кнопки головної та відображення сторінок із активністю.
  Якщо активний розділ більше недоступний, повернути користувача на головну.
- При помилці маніфесту показувати стан помилки; не припускати, що всі модулі активні.
  Помилку API активного модуля відрізняти від порожнього списку записів.
- Застосувати аналогічну поведінку до React UI у `frontend/src`, зокрема резервного
  маніфесту та повторного завантаження конфігурації.
- Перевірити всі три дизайни: `classic`, `editorial`, `portal`.

### 5. Перевірити встановлений пакет і додати CI

Матриця функціональних сценаріїв:

| Конфігурація | Очікування |
| --- | --- |
| Усі модулі | Чинні функції й URL працюють |
| Тільки core | Головна, профіль, маніфест, аудит та адмінка працюють |
| Кожен незалежний модуль окремо з core | Немає прихованих залежностей |
| core + admissions + schedule | Розклад працює з мінімальною залежністю |
| Повний набір без кожного модуля | API, схема і меню виключають цей модуль |
| Повний набір без admissions і schedule | Валідне спільне вимкнення залежних модулів |
| schedule без admissions | Зрозуміла помилка конфігурації |
| Вимкнення і повторне ввімкнення gallery | Збережені записи знову доступні |

Для сценарію «без admissions» із залишеним schedule очікується помилка залежності.
Для валідних конфігурацій перевіряти `check`, `migrate`, `makemigrations --check`,
генерацію OpenAPI, HTTP-відповіді, демодані та адміністративну панель.

- Розширити `scripts/smoke_installed_package.py`: один зібраний wheel встановлюється
  у чисте середовище, кілька проєктів запускаються поза checkout в окремих процесах.
  Probe має враховувати склад модулів замість безумовного імпорту моделі safety.
- Повну матрицю виконувати на Linux; на Windows — повний, мінімальний і залежний набори.
- Зібрати всі три згенеровані фронтенди. Додати поведінкові браузерні перевірки
  меню й мережевих запитів для скороченого набору та недоступного маніфесту.
- Перевірити, що відключені API справді не запитуються, а не лише приховуються
  за обробкою помилок. Додати перевірку повторного завантаження маніфесту в UI kit.

### 6. Документація та завершення

- Оновити README й архітектурну документацію: мінімальний `INSTALLED_APPS`, таблиця
  залежностей, підключення спільних маршрутів, перезапуск, збереження даних.
- Додати інструкцію для раніше згенерованих сайтів: оновлення пакета саме по собі
  не переписує їхні `urls.py` або фронтенд. Показати цільові ручні зміни;
  попередити про перезапис власних правок при повній регенерації фронтенду.
- Виконати рев'ю змін, чинні backend-тести й frontend build, нову матрицю та
  перевірки встановленого wheel. Зафіксувати фактичні результати.

## Критерій завершення

Будь-яка підтримана перевірена конфігурація запускається зі встановленого пакета;
вимкнені модулі не створюють імпортних помилок, зайвих API-запитів або недоступних
посилань. Некоректна залежність має зрозумілу діагностику. Повний сайт зберігає
поточну поведінку, дані переживають вимкнення, а CI запобігає повторенню проблем.

## Межі задачі

Окремо залишаються ролі редакторів, відкладена публікація, багатомовність,
нові дизайни, сторонні плагіни та публікація релізу. Наявна зміна
`frontend/package-lock.json` потребує окремого перегляду перед включенням у коміт.

## Результати перевірок

- 32 Django-тести та перевірка OpenAPI пройшли; `makemigrations --check --dry-run`
  не виявила змін моделей.
- Встановлений wheel перевірено поза каталогом вихідного коду: повний сайт,
  лише `core`, кожен незалежний модуль, повний набір без окремих модулів,
  `admissions + schedule` та відсутність обох. `schedule` без `admissions`
  видає `school.E001`. Повторне ввімкнення `gallery` повертає збережені записи.
- У локальному середовищі немає доступу до PyPI. Для wheel-тесту залежності
  взято з наявного venv; CI перевіряє чисте встановлення на Linux і Windows.
- UI kit пройшов тести й збірку; згенеровані `classic`, `editorial`, `portal`
  окремо пройшли TypeScript і Vite збірку.
- Графічну перевірку через Firefox виконати не вдалося: headless браузер у цьому
  середовищі завершувався або зависав до першого HTTP-запиту. Мережеву поведінку
  фронтенду додатково слід перевірити в браузері під час ручного приймання.
