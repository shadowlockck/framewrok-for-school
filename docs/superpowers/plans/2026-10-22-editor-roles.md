# Ролі редакторів у Django School Framework

Статус: реалізовано 2026-10-22. Перевірки SQLite та встановленого wheel пройдено;
окремий MySQL job додано до CI, його виконання очікується після запуску workflow.

Репозиторій: `/home/shadowlock/work/myprojects/framework for school`.

Рішення користувача: **редактор може сам публікувати матеріали** у дозволених йому розділах.

## 1. Результат для користувача фреймворку

Розробник створює сайт, застосовує міграції та запускає команду налаштування ролей.
Технічний адміністратор створює обліковий запис працівника, дозволяє вхід до адмінки
і призначає одну або кілька готових груп. Працівник бачить доступні йому розділи,
редагує їхні матеріали та самостійно публікує. Пряме відкриття URL або підроблений
POST не дають доступу до чужих розділів.

Права діють на всі записи дозволених моделей у цьому екземплярі сайту школи.
Обмеження «лише власні матеріали» потребувало б окремого поля автора та іншої
моделі доступу; у цій задачі редактори одного розділу працюють зі спільним вмістом.

## 2. Поточний стан, підтверджений кодом

- Використовуються Django 5.2, Django Admin і стандартна система авторизації.
- У кожному модулі вже є `ModelAdmin`; власного реєстру ролей і команди груп немає.
- `NewsArticle.is_published` керує видимістю новин. API віддає лише опубліковані новини.
  В інших моделей є власні ознаки активності або публічність після збереження.
- Публічні API побудовані на `ReadOnlyModelViewSet`. Виняток — анонімне створення
  `ConfidentialReport`, без читання списку чи окремого звернення через API.
- `ConfidentialReportAdmin` вже робить вхідні дані звернення незмінними;
  редагованими залишаються `is_reviewed` і `review_notes`.
- `ThemeSettings`, `GalleryPhoto`, `EnrolledStudent` присутні також у вкладених формах.
- `schedule.LessonSchedule.grade` залежить від `admissions.ClassCapacity`.
  Видалення класу каскадно зачіпає учнів і, коли модуль установлено, уроки.
- Віджет аудиту на головній адмінки зараз показує посилання на всі активні розділи,
  не враховуючи права конкретного працівника.
- Реєстр модулів у `apps.core.modules` уже враховує `INSTALLED_APPS` та AppConfig.
- Є CI для backend, OpenAPI, frontend та встановленого wheel на Linux і Windows.
- Вихідний план згадував `SuperAdmin`, `ContentAdmin`, `Teacher` та можливі кабінети
  батьків/учнів. Ця задача конкретизує адміністратора й редакторів. Професія «вчитель»
  сама по собі не надає прав: працівнику призначають потрібні редакторські групи.

## 3. Матриця ролей

`CRUD` у таблиці означає стандартні `view`, `add`, `change`, `delete`.
Редактор може публікувати та знімати з публікації там, де модель має відповідне поле.
Для інших моделей збереження працює за їхньою поточною публічною семантикою.

| Ідентифікатор | Назва для адміністратора | Моделі та дозволи |
| --- | --- | --- |
| Стандартний superuser | Технічний адміністратор | Усі права, керування користувачами та групами. Створюється через `createsuperuser`, окрема група не потрібна. |
| `content_admin` | Головний редактор | CRUD усіх явно перелічених нижче публічних моделей активних модулів; `view/change` для `core.SchoolProfile` і `core.ThemeSettings`. Профіль і тему початково створює адміністратор. |
| `news_editor` | Редактор новин | CRUD `news.NewsCategory`, `news.NewsArticle`, включно з `is_published` та `is_urgent`. |
| `legal_editor` | Редактор документів і відомостей | CRUD `legal.LegalDocumentCategory`, `legal.LegalDocument`, `legal.StaffMember`, `legal.Vacancy`. |
| `finance_editor` | Редактор фінансової звітності | CRUD `legal.FinancialReport`. |
| `admissions_editor` | Редактор вступу | CRUD `admissions.ServiceTerritory`, `admissions.ClassCapacity`, `admissions.EnrolledStudent`, `admissions.AdmissionLottery`. |
| `nutrition_editor` | Редактор харчування | CRUD `nutrition.CateringProvider`, `nutrition.DailyMenu`. |
| `schedule_editor` | Редактор розкладу | CRUD `schedule.BellSchedule`, `schedule.LessonSchedule`; лише `view` для `admissions.ClassCapacity`. |
| `gallery_editor` | Редактор галереї | CRUD `gallery.PhotoAlbum`, `gallery.GalleryPhoto`, включно з вкладеними фото. |
| `safety_editor` | Редактор публічного розділу безпеки | CRUD тільки `safety.AntiBullyingPolicy`. |
| `reports_reviewer` | Відповідальний за конфіденційні звернення | `view/change` тільки `safety.ConfidentialReport`; зміна статусу опрацювання та службових приміток. |

Головний редактор охоплює всі публічні ролі, включно з фінансами, але не
`reports_reviewer`. Прав на користувачів, групи, permissions, sessions чи службові
моделі він не отримує. Редактор документів не отримує фінансові права автоматично.

Одна людина може поєднати, наприклад, `news_editor` і `gallery_editor`, або
`safety_editor` та `reports_reviewer`. Для останньої ролі створення й видалення
звернень через адмінку не дозволені; технічний superuser зберігає свої повноваження.

## 4. Контракт авторизації

1. Ролі реалізуються стандартними `django.contrib.auth.models.Group` і `Permission`.
   Джерело фактичного доступу — Django permissions, а не порівняння назв груп у view.
2. Вхід до адмінки потребує `is_active=True` та `is_staff=True`. Сам `is_staff`
   не надає права редагувати моделі. Команда ролей не змінює ці прапорці користувачів.
3. Облікові записи й групи призначає технічний адміністратор через чинну Django Admin.
   Редакторські групи не дають прав підвищувати власні повноваження.
4. Права кількох груп та індивідуальні permissions додаються. При відкликанні ролі
   доступ зникає лише якщо користувач не має такого ж дозволу з іншого джерела.
   Це треба явно пояснити в інструкції адміністратора.
5. Обмеження забезпечують серверні перевірки `ModelAdmin` та `InlineModelAdmin`.
   Не вводити власний middleware, authentication backend, нову модель User чи
   дублююче поле `role`.
6. Нові групи не отримують дозволів на майбутні моделі автоматично: список моделей
   та операцій є явним. Нова модель потребує свідомого оновлення матриці.
7. Приклад і тести працюють через `get_user_model()`. Підтримати звичайний Django User
   і сумісний `AUTH_USER_MODEL` з `PermissionsMixin`; власну адмінку нестандартного
   User налаштовує проєкт, який використовує фреймворк.
8. Межа даних — окремий екземпляр сайту школи. Ці групи не реалізують ізоляцію кількох
   шкіл усередині спільної БД.

Публічні API залишаються доступними для читачів. Додавання редактора не відкриває
запис через REST API. Публічне створення конфіденційних звернень зберігається;
читання звернень через API не додається навіть для авторизованого працівника.

## 5. Реєстр і налаштування груп

### 5.1. `backend/apps/core/roles.py`

Створити явний реєстр із незмінними описами ролей: стабільний ключ, назва групи,
залежності від модулів і перелік `app_label.model_name → операції`.

- Назви готових груп мають префікс `Шкільний фреймворк: ` і українську назву з таблиці.
  Вони сталі та не залежать від поточної мови інтерфейсу.
- Назви є ідентифікаторами керованих груп; для власного набору прав адміністратор
  створює окрему групу з іншою назвою.
- Реєстр зберігає рядкові ідентифікатори моделей. Імпорт необов'язкових моделей
  на рівні модуля не допускається. Розв'язання відбувається через registry Django
  після перевірки активності модулів.
- Очікувані permissions визначаються за `content_type.app_label`,
  `content_type.model` і точним `codename`, а не лише за назвою застосунку.
- `content_admin` складається з явного переліку публічних прав активних модулів
  і прав на профіль/тему. `ConfidentialReport` не потрапляє до цього переліку.
- Вимкнений `schedule` не створює роль розкладу; активний `schedule` без `admissions`
  продовжує давати чинну помилку `school.E001`.

### 5.2. Команда `setup_school_roles`

Новий файл: `backend/apps/core/management/commands/setup_school_roles.py`.

```bash
python manage.py migrate
python manage.py setup_school_roles --dry-run
python manage.py setup_school_roles
```

Контракт команди:

1. Працює після `migrate`, коли Django вже створив стандартні permissions.
2. До першого запису перевіряє наявність таблиць auth/contenttypes та всіх очікуваних
   permissions активних моделей. За відсутності завершується з ненульовим кодом
   і повідомленням українською про необхідність міграцій. Не створює permissions вручну.
3. Створює відсутні групи активних ролей, а для наявних керованих груп установлює
   точний актуальний набір permissions. Випадково додані зайві права прибираються.
4. Для неактивної ролі нову групу не створює; з існуючої керованої групи прибирає
   permissions, зберігаючи саму групу й членство користувачів. Після повторного
   ввімкнення модуля повторний запуск повертає визначені роллю права.
5. Не редагує сторонні групи, членство користувачів, індивідуальні дозволи,
   паролі чи `is_staff/is_superuser`. Зміни наборів permissions виконуються атомарно.
6. Повторний запуск без змін конфігурації не змінює результат. `--dry-run` тільки
   показує створення груп, додавання/вилучення прав і відключені ролі; записів немає.
7. `--database` обирає DB alias, за замовчуванням `default`. Group, Permission і
   ContentType мають бути в тій самій БД; несумісний router має дати зрозумілу помилку.
   Розподілена система auth між кількома БД не є ціллю задачі.
8. Вивід українською містить підсумок змін та нагадування про призначення груп
   і `is_staff`. Лог не містить персональних даних користувачів.

Не запускати налаштування груп в `AppConfig.ready()`, при HTTP-запиті чи після
кожної міграції сигналом. Адміністратор явно синхронізує ролі після встановлення,
оновлення їхнього контракту або зміни набору модулів. Ручні зміни всередині готових
груп перезаписуються цією командою; власні групи залишаються під контролем проєкту.

Після вимкнення модуля недоступність його маршрутів та моделей забезпечується
чинною модульною архітектурою одразу після перезапуску. Команда окремо впорядковує
збережені права. Сталі права зі сторонніх груп чи `user_permissions` вона не очищає.

### 5.3. Схема БД та оновлення

Зміни моделей і нові schema/data-міграції не потрібні: використовуються наявні таблиці
auth. Стандартні permissions створюються на `post_migrate`, тому наповнення груп
винесене в команду після міграцій і враховує фактичний склад установлених модулів.
`makemigrations --check --dry-run` має залишитися чистим.

Оновлення пакета саме по собі не змінює права чинних працівників. Для нового сайту
команду додати до README, який генерує CLI; для наявного — до посібника оновлення.

## 6. Поведінка адмінки та публікації

### 6.1. Модельні та вкладені форми

- Використати чинні серверні перевірки Django Admin; додатковий код у `admin.py`
  додавати тільки там, де поведінкові тести виявлять реальний обхід.
- Новини: редактор може зберегти чернетку, опублікувати, зняти з публікації,
  змінити категорію й позначку терміновості. Не змінювати поточне значення
  `is_published` за замовчуванням або семантику `published_at` у цій задачі.
- Галерея: створення/редагування/видалення фото у вкладеній формі та окремій адмінці.
- Вступ: вкладені учні потребують власних permissions. Наявність тільки права
  перегляду класу не відкриває список учнів чи їхні вкладені форми.
- Розклад: список класів доступний для вибору, але кнопки створення/зміни класу
  та прямі POST до ClassCapacity заборонені редактору розкладу.
- Каскадне видалення класу, який має уроки, не повинно обходити відсутнє право
  `delete_lessonschedule`. Перевірити окреме та масове видалення.
- Профіль/тема: головний редактор редагує вже створені дані; початкове створення
  й видалення залишаються технічному адміністратору.
- Звернення: `reports_reviewer` змінює тільки опрацювання й примітки. Підроблені
  значення тексту звернення, контактів, ролі заявника та дати не зберігаються.
- Зберегти штатний журнал дій Django Admin. Нової системи історії версій не вводити.

### 6.2. Віджет аудиту

У `compliance_tags.py` додати обробку контексту запиту для адмінського представлення
звіту. Для кожного критерію визначати цільову модель через явне зіставлення його
стабільного `code` з моделлю та отримувати зареєстрований `ModelAdmin` через
`admin.site.get_model_admin()` після `is_registered()`.

- Посилання на changelist формувати через `reverse()` тільки коли
  `has_view_permission(request)` або `has_change_permission(request)` дозволяє доступ.
- У шаблоні виводити кнопку лише за наявності дозволеного посилання.
- Підсумковий відсоток та кількість перевірок залишаються оцінкою всього активного
  публічного вмісту школи, а не лише розділів редактора.
- Не змінювати JSON-контракт публічного аудиту. Працювати з окремою копією даних
  для адмінського віджета; не кешувати персоналізовану відповідь між користувачами.
- Вимкнені модулі та `core`-only конфігурація мають відображатися без помилок.

## 8. План перевірок

### 8.1. Реєстр і команда

- Точні набори permissions кожної ролі; головний редактор не має auth або звернень.
- Повторний запуск; `--dry-run` без записів; атомарний відкат при помилці.
- Відсутні таблиці/permissions: зрозуміла помилка до будь-яких змін груп.
- Випадково додане небезпечне право в керованій групі прибирається синхронізацією.
- Членство, індивідуальні дозволи, прапорці користувачів та власні групи збережені.
- Потрібний DB alias використовується для всіх операцій; несумісний router відхиляється.

### 8.2. Реальні HTTP-запити до Django Admin

Перевіряти наслідок запиту в БД разом зі статусом відповіді. Одного виклику
`user.has_perm()` або перевірки наявності кнопки недостатньо.

| Обліковий запис / дія | Очікування |
| --- | --- |
| Анонімний, неактивний або користувач без `is_staff` | Адмінка не відкриває дані чи редагування. |
| `is_staff=True`, без permissions | Адмінський вхід сам по собі не дозволяє роботу з моделями. |
| Кожна редакторська роль | Дозволені list/add/change/delete працюють для її моделей; чужі модельні GET/POST відхиляються. |
| Редактор новин | Збереження, публікація та зняття з публікації змінюють видимість у публічному API. |
| Новини + галерея | Обидва розділи доступні, фінанси й звернення недоступні. |
| Головний редактор | Увесь публічний контент і редагування профілю; без auth/group management та звернень. |
| Редактор розкладу | Вибір класу дозволений; зміна класу, перегляд учнів та обхід через popup/inline заборонені. |
| Редактор вступу без прав розкладу | Не може каскадно видалити уроки через видалення класу чи bulk action. |
| Редактор безпеки | Працює з політикою; list/detail/change/history звернень недоступні. |
| Відповідальний за звернення | Читає звернення й змінює службові поля; не створює/видаляє їх і не підміняє вихідні дані. |
| Користувач лише з `view` | GET дозволений, POST і вкладені зміни відхиляються. |
| Технічний superuser | Чинний повний доступ збережено. |

Додатково: перевірити CSRF на адмінських POST через `Client(enforce_csrf_checks=True)`,
bulk delete, прямі URL, вкладені форми та повідомлення про відмову. Відмова для
авторизованого staff за наявного маршруту очікується як 403; вимкнений модуль — 404;
користувач без доступу до входу — перенаправлення/відмова входу.

Перевірити відкликання групи в наступному HTTP-запиті та збереження доступу,
якщо ідентичне право надає інша група. Не покладатися на кеш permissions уже
завантаженого об'єкта User. Окремий ізольований тестовий проєкт із сумісним custom
User підтверджує відсутність жорсткої залежності від `auth.User`.

### 8.3. Публічний контракт і модульність

- Анонімне читання публічних даних працює; CRUD через публічні read-only API не з'являється.
- Неопублікована новина не потрапляє до списку чи detail endpoint.
- Звернення можна надіслати, але не отримати список/деталі, змінити чи видалити через API,
  навіть із редакторською або суперкористувацькою сесією.
- Віджет не має недоступних посилань і не змінює оцінку школи залежно від ролі.
- Матриця модулів: усі; тільки `core`; лише `news`; лише `safety`; `admissions + schedule`;
  відключення та повторне підключення `gallery` зі збереженням членства й записів.
- Розклад без вступу дає `school.E001`. Відсутність моделі не спричиняє імпортної помилки.

### 8.4. Пакет, БД та CI

- У smoke-тесті після `migrate` запускати `setup_school_roles` двічі, перевіряти
  відсутність дублювання та базові дозволи редактора реальним HTTP-запитом.
- Перевірки виконувати із wheel поза checkout. Використати чинну матрицю Linux
  Python 3.11/3.12 та Windows Python 3.12, включно з конфігураціями модулів.
- Додати до `.github/workflows/ci.yml` окремий job із MySQL 8.0 для `apps.core.test_roles`,
  щоб перевірити групи, транзакційність і видалення також на СУБД проєкту.
  Чинні швидкі SQLite-перевірки залишаються частиною backend job.
- Виконати чинні backend-тести, `check`, `makemigrations --check --dry-run`, валідацію
  OpenAPI, перевірки встановленого пакета та наявні CI-збірки. Окремі нові frontend
  тести не потрібні: в цій задачі інтерфейс редагування — Django Admin.
- У браузері пройти вхід редактора новин, головного редактора та відповідального за
  звернення, додавання/публікацію новини, відсутність чужих меню й роботу посилань аудиту.
  Для цього використовувати тестовий сайт і демонстраційні звернення.
- Якщо локально MySQL, мережа чи браузер недоступні, позначити відповідну перевірку
  як невиконану, а не зараховувати їй успіх; завершення підтвердити результатом CI
  або доступного середовища приймання.

## 9. Інструкція адміністратора, яку треба додати

1. Після встановлення: `migrate` → `setup_school_roles` → `createsuperuser`.
2. Технічний адміністратор початково створює профіль і тему, якщо їх ще немає.
3. У «Користувачах» створює працівника, установлює пароль, `is_active` та `is_staff`,
   обирає одну або кілька редакторських груп; `is_superuser` для редактора вимкнений.
4. Працівник входить у `/admin/`; публікація відбувається через чинні форми модулів.
5. Для відкликання доступу прибирають групи й перевіряють індивідуальні дозволи;
   для блокування всього облікового запису вимикають `is_active`.
6. Після зміни модулів/оновлення матриці ролей: `migrate`, перегляд `--dry-run`,
   виконання `setup_school_roles`, перевірка доступу працівників.
7. Власні набори прав створюють окремими групами; керовані групи повертаються
   до матриці при синхронізації. Команда не призначає працівникам груп автоматично;
   зміна прав уже призначеної групи поширюється на всіх її учасників, тому її видно
   в попередньому перегляді `--dry-run`.

## 10. Критерії завершення та межі

Готова задача означає, що зі встановленого пакета можна підняти сайт, налаштувати
ролі однією командою, створити редактора й виконати весь його робочий сценарій.
Дозволені публікації працюють, недозволені операції не змінюють БД, конфіденційні
звернення відокремлені, вимкнені модулі враховані, повторне налаштування передбачуване.
Документація, CI та результати перевірок відповідають реалізації.

Ця задача не додає погодження матеріалів, планувальника публікацій, кабінетів
учнів/батьків, обмеження за автором, нового frontend-редактора, нової моделі User,
нової системи історії чи сторонніх RBAC-залежностей. Це окремі можливості.
Коміт і реліз PyPI — подальші кроки після реалізації та перевірок.

Під час планування в робочому дереві вже змінено `frontend/package-lock.json`.
Цю зміну треба розглядати окремо від задачі ролей. Репозиторій лендінгу до неї не входить.
